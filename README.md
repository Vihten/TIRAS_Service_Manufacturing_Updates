# TIRAS Service Manufacturing Updates

Публічний канал готових Windows-збірок **TIRAS Service Manufacturing**.
Вихідний код застосунку зберігається окремо у приватному репозиторії.

## Завантаження та встановлення

[**Завантажити інсталятор 1.0.49 для Windows x64 — EXE**](https://github.com/Vihten/TIRAS_Service_Manufacturing_Updates/releases/download/v1.0.49/TIRAS-Service-Manufacturing-1.0.49-Online-Setup-x64.exe)

Завантажте лише цей EXE та запустіть його. Інсталятор сам завантажить решту
файлів через інтернет, перевірить SHA-256 і встановить застосунок.
Вручну завантажувати чи розпаковувати архіви не потрібно. Файл `*-payload.7z`
у релізі — внутрішній ресурс інсталятора, його не потрібно відкривати.

Потрібні Windows 10 версії 1703 або новіша / Windows 11, x64, та доступ до
інтернету. Visual C++ Runtime і засоби прошивання входять до пакета;
Flutter, Python та 7-Zip окремо встановлювати не потрібно.

Інсталятор працює для поточного користувача й автоматично створює ярлики.
Після першого встановлення можна вибрати, чи відкрити застосунок; після оновлення
він відкривається автоматично. Сам інсталятор не прошиває пристрої, але відкритий
застосунок може почати оновлення підключеного сумісного пристрою.
Для оновлення завершіть роботу з пристроями, закрийте застосунок і виберіть
його поточну папку. Рекомендовано залишити стандартний шлях: надто довгі
вкладені шляхи можуть перевищити обмеження Windows.

EXE не має цифрового підпису видавця. Контрольні суми й відомі обмеження —
в [останньому релізі](https://github.com/Vihten/TIRAS_Service_Manufacturing_Updates/releases/latest).

## Оновлення самого застосунку

Версія 1.0.1 не вміє перевіряти оновлення застосунку. Для першого переходу
на актуальну версію завершіть операції з пристроями, закрийте програму та один раз
запустіть EXE за посиланням вище.

Починаючи з 1.0.2, застосунок може повідомляти про наступні версії через
публічний канал GitHub Releases. Завантаження й запуск оновлення потребують
дії користувача. Перед запуском перевіряються розмір і SHA-256 інсталятора.
SHA-256 підтверджує відповідність файлу метаданим релізу та не замінює
цифровий підпис видавця. Оновлення застосунку й прошивання пристроїв —
окремі операції.

Версію 1.0.3 відкликано. Не встановлюйте її; використовуйте актуальний
інсталятор за посиланням вище. Починаючи з 1.0.4, перевірка нових версій
читає публічний файл `latest.json` без звернення до GitHub API на вашому ПК.

## Режими роботи

У звичайному режимі програма автоматично виявляє сумісні пристрої TIRAS і
запускає оновлення, якщо воно потрібне. Прошивки завантажуються з GitHub;
не від'єднуйте пристрій під час запису.

Для перегляду інтерфейсу без звернення до пристроїв запустіть встановлений
`TIRAS_Service_Manufacturing.exe` з `--preview`.
Перед виробничим використанням нової версії проведіть контрольне випробування
на пристроях. Відомі обмеження наведено в описі кожного релізу.

## Розмір

Актуальні розміри EXE та автоматично завантажуваного пакета наведено
серед файлів відповідного релізу.
Під час встановлення додатково потрібне місце для тимчасового пакета.

## Сторонні компоненти

Пакет містить оригінальний esptool 5.3.1 із підписом Espressif та його ліцензію.
[Вихідний код esptool](https://github.com/espressif/esptool/tree/v5.3.1).
Ліцензії Flutter/Dart-залежностей і повідомлення про Visual C++ Runtime
також включені до пакета.

## Публікація релізу

Цей репозиторій містить лише документацію, workflow, `latest.json` та готові публічні
файли релізів. Вихідний код застосунку, локальні звіти, журнали й тестові
інсталятори тут не публікуються.

Для кожного стабільного тегу `vMAJOR.MINOR.PATCH` у папку
`release-assets/<tag>/` додаються рівно чотири файли:

- `TIRAS-Service-Manufacturing-<version>-Online-Setup-x64.exe`;
- `TIRAS-Service-Manufacturing-<version>-payload.7z`;
- `TIRAS-Service-Manufacturing-<version>-windows-x64.update.json`;
- `SHA256SUMS.txt` із SHA-256 перших трьох файлів.

Маніфест оновлення має поля `schemaVersion` (1), `version`, `channel`
(`stable`), `installerAsset`, `sha256` і `size`. Назва інсталятора, його
SHA-256 та розмір у байтах мають відповідати EXE цього самого тегу.
Застосунок читає маніфест із релізу, а інсталятор містить зафіксовані URL,
розмір і SHA-256 свого пакета.

Push тегу запускає `publish-app-release.yml` із репозиторним `GITHUB_TOKEN`.
Workflow перевіряє склад файлів, контрольні суми та маніфест, створює
чернетку релізу, завантажує пакет першим, потім EXE, маніфест і контрольні
суми. Усі завантажені файли повторно перевіряються. Після відкриття релізу
workflow перевіряє анонімне завантаження й лише тоді позначає реліз як
`latest`. Незавершена чернетка може бути продовжена повторним запуском.
Якщо перевірка перервалася після публікації, повторний запуск перевіряє
всі чотири наявні файли та анонімний доступ, а потім завершує позначення
`latest`. Вже опубліковані файли workflow не додає й не замінює.
Повторний запуск старого тегу не змінює `latest`, якщо там уже новіша версія.
Тег відкликаної версії `v1.0.3` workflow не публікує й не відновлює.
Після перевірки публічних файлів і позначення релізу як `latest` workflow
оновлює `latest.json` у `main`. Маніфест каналу зберігає формат метаданих
GitHub Release та не випереджає перевірену публікацію. Перезапуск старої
версії не знижує версію каналу; конкурентну зміну файла захищає перевірка SHA.

Перед push потрібно звірити локальні файли з `online-installer-report.json`
у приватній робочій папці. Звіт до публічного репозиторію не додається.
Опублікований пакет не замінюйте: наступна збірка потребує нової версії
з відповідними EXE, пакетом і маніфестом. Перевірка публікації не замінює
випробування встановлення та роботи з фізичними пристроями.
